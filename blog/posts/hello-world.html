Hello, world

25 Oct 2026 — 3 min read

This is the first post on a site that, until now, was just a name and a list of things I know how to do. I wanted a place to think in public, away from feeds and timelines, about the work that takes up most of my days: backend systems and the infrastructure underneath them.

No newsletter popup. No reading progress bar. Just text, hyperlinks, and the occasional code block.

What goes here

I plan to write about the parts of engineering that are easy to get wrong and hard to learn from a tutorial:

  • Backend design decisions, and the trade-offs I only understood later.
  • Cloud architecture and infrastructure as code, including the failure modes.
  • Debugging notes — the kind that save someone an afternoon.
  • Small tools and habits that make systems easier to operate.

Writing to think

A design only feels finished once I have tried to explain it. Writing forces that test. If a paragraph needs three caveats to survive, the design probably needs another look.

The best documentation is the kind you write for yourself six months from now.

For example, most production issues I have seen reduce to something like this:

curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" \
  https://example.com/health

Boring, repeatable checks beat clever dashboards when something is on fire.

How this works

This blog is static HTML and one stylesheet. There is no framework, no build step, and no database. Adding a post means copying a template, writing the content, and adding one line to the index. That is a feature, not a limitation.
